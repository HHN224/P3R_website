# 问它目录里有什么，它却试了十次也没答上来

> 日期：2026-08-21
> 项目：agent-lite，一个我用 Python 练习做的编程助手

昨天刚把助手做成一个随时能启动的命令，今天我就问了它一个再普通不过的问题：“帮我看看当前目录有什么文件。”

它没有回答，反而一连执行了十次命令，最后说自己已经达到调用次数上限。从屏幕上看像是卡死了；翻开保存的对话才发现，它一直在工作，只是每次拿到的都是同一句莫名其妙的错误。它不知道错在哪里，只好换个命令再试，直到把十次机会用完。

## 错误指向的地方，原来不是问题所在

报错的大意是“不能把空值和文字拼在一起”。我起初也顺着这句话查，怀疑是不是命令没有输出。可同一个目录里，有的命令成功，有的失败；有时还能看到中文文件名变成乱码。这些现象放在一起，才让我想到输出文字是怎么从容器传回 Windows 的。

命令在 Linux 容器里运行，那里把中文转换成 UTF-8 字节。我的电脑是中文 Windows，Python 却按系统默认的 GBK 去读这些字节。两边像在用不同的字典：有些内容被误读成乱码，程序还能继续；碰上 GBK 无法解释的字节组合，读取输出的后台线程就出错了。

更绕的是，我的代码并没有直接看到“编码错误”。在这次复现里，读取失败后，命令的输出变成了空值；代码接着把它与错误信息拼接，才抛出那个“空值加文字”的错误。助手看到的是最后一步的报错，自然猜不到真正的原因。

## 我改了什么

我不再让 Python 根据 Windows 的默认设置自动解读命令输出。现在先接收原始字节，再明确按 UTF-8 转成文字。遇到少量无法解读的字节，就用替代字符表示，而不是让整次工具调用失败。Windows 终端打印这些字符时，也加了一层保护，避免结果已经读进来了，却在显示给我看时再次出错。

修改后，我用测试重现了空输出、中文文件名和异常字节的情况，还在真实容器里跑了带中文的命令。原来的“试十次也答不上来”不再由这个编码问题触发。

这次排查让我记住一件事：助手反复试错，不一定是模型没理解任务。它可能从工具那里收到一条完全误导人的错误。对跨 Windows 和 Linux 的输出，先说清使用什么编码；对失败，也尽量告诉助手可以采取什么行动。否则一个简单的“看看目录”，就会变成十次没有意义的尝试。
