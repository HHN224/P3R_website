# 模型一直在思考，为什么压缩摘要还是空的？

日期：2026-09-30
项目：agent-lite，一个我用 Python 练习做的编程助手

对话变长以后，我的 Agent 会把前面的记录整理成摘要，腾出空间继续工作。这个功能听起来很简单：把旧消息交给模型，让它留下目标、进展和还没解决的问题。

但在一次真实会话里，压缩请求跑了十几秒，最后却没有留下一个字的摘要。返回的结束原因是 `finish_reason=length`。重试之后，结果还是一样。

这篇记录整理的是 9 月 18 日的一次修复。最让我意外的地方是：请求确实在消耗输出额度，但我需要的正文还没有开始。

## 摘要为空，不一定是模型没有工作

当时我把压缩摘要的目标长度设成了 2,000 tokens，也把这个数字直接传给 API，当作本次请求的硬输出上限。我以为“希望摘要写多长”和“允许这次生成消耗多少额度”是一回事。

这个假设在当时使用的模型路由上不成立。它在输出正文之前，会先消耗一部分额度进行推理。额度花完以后，服务端用 `length` 结束生成，而压缩器没有收到可用的正文片段。

所以我看到的是一个很别扭的现象：模型一直在处理请求，程序却只能拿到空摘要。等待时间不能证明正文已经生成；结束原因也不能单独告诉我，额度究竟花在了哪一部分。

## 先只改一个变量

我最初也怀疑过：是不是历史太长，或者需要再缩小压缩区间？为了确认，我拿同一段真实会话做了对照。原始区间有 56,726 个字符，下面的字符数都指文本长度，不是 token 数。

| 尝试 | 输入区间 | API 输出上限 | 结果 |
| --- | --- | --- | --- |
| A：保持默认参数，连续三次 | 56,726 字符 | 2,000 tokens | 全部以 `length` 结束，没有可用摘要 |
| B：只缩短输入 | 15,000 字符 | 2,000 tokens | 仍然以 `length` 结束 |
| C：保留原输入，只增加输出额度 | 56,726 字符 | 8,000 tokens | 13.2 秒得到 3,237 字符的摘要 |

把输入缩短没有救活这次压缩；保留原输入、只提高输出上限，却拿到了正文。至少对这段会话和这个路由来说，继续削减历史没有解决真正卡住的地方。

这组实验让我把排查重点放回了输出预算：我给模型留了写摘要的目标，却没有给它留出在写之前完成推理的余地。

## 把目标长度和生成预算分开

修复时，我保留了 `max_tokens` 作为提示词里的摘要长度目标，又增加了 `output_tokens`，专门控制发给 API 的硬上限。未显式指定时，采用下面的默认值：

```python
MIN_SUMMARY_OUTPUT_TOKENS = 6000
api_output_tokens = output_tokens or max(
    max_tokens * 4,
    MIN_SUMMARY_OUTPUT_TOKENS,
)
```

这样，默认目标仍是 2,000 tokens，但 API 可以使用 8,000 tokens 的额度。目标设成 1,234 时，上限至少是 6,000；目标设成 4,000 时，上限随之变成 16,000。需要时，也可以单独覆盖硬上限。

这里的四倍和 6,000 是项目当前的默认策略，不是所有模型都适用的公式。不同接口如何计算推理与正文的额度，需要按实际路由确认。对我来说，关键是终于把两个含义不同的参数分开了，之后才有办法分别调整摘要长度和生成成本。

## 被截断的正文，也不该直接丢掉

我还顺手改了对 `length` 的处理。以前只要看到这个结束原因，就把整次摘要判为失败。可“达到上限”也可能发生在模型已经写出一部分正文之后。

现在，如果已经收到非空的正文片段，就把它保留下来，交给后续的摘要校验；如果一个正文片段都没有，仍然报错。模型真的尝试调用工具，也仍然会被拒绝，因为压缩这一步只应该整理已有记录。

保留正文不等于直接用它替换历史。截断的内容可能缺少未完成事项，也可能结构不完整，是否能作为摘要仍由后续校验决定。我想避免的是：仅凭一个结束标记，就把本来值得检查的内容全扔掉。

## 压缩失败以后，别每一轮都重新撞一次

输出预算解释了这次空摘要，但失败之后怎么继续运行，也是另一个问题。

此前的修复已经给自动压缩加了退避：一次失败后，要等新增足够的消息再试；连续失败达到上限，就停止自动尝试。否则，每一轮工具调用都可能重新等一次压缩，用户看到的就是助手反复停下来。

项目里也准备了不依赖模型的机械摘要，用已有记录提取目标、文件、命令和最近的结论，并明确标注它的性质。它能保留有限线索，却不能当作模型已经恢复的证据。只有真正的模型摘要成功，才应该重置对应的失败状态。

这几层处理各有用途：预算让这次生成有机会写出正文，退避减少重复等待，机械摘要则在生成不可用时尽量留下继续工作的依据。

## 回到同一段会话验证

修改后，我用同一段真实区间和默认参数再做了一次压缩：`compact_now` 返回成功，用了 16.3 秒，折叠了 247 条消息，产生 3,452 字符的摘要并通过校验。请求载荷从约 320 万字符降到约 104 万字符。

这些数字只描述这次验证，不能保证所有会话都会以相同速度或比例压缩。它至少回答了最初的问题：旧记录并非不能总结，而是此前给出的硬输出额度，让正文没有机会出现。

以后再遇到“模型跑了很久，但结果是空的”，我会先把几个问题分开看：正文片段有没有出现？请求怎样结束？输出上限覆盖了哪些消耗？改变一个参数后，结果是否随之改变？

这次踩坑提醒我，一个叫作“摘要长度”的数字，一旦放进 API 请求里，就可能变成完全不同的约束。参数名看起来合理，还不够；得确认它在整条生成链路里真正限制了什么。
