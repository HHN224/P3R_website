# 我以为把命令放进 WSL 就安全了

> 日期：2026-09-09
> 项目：agent-lite，一个我用 Python 练习做的编程助手

我的助手能替我运行命令。这个能力很方便，也意味着它可能改动文件。我给它准备了几种运行环境，其中一种是 WSL：Windows 里的 Linux 环境。起初我觉得，既然命令已经在一个 Linux 虚拟环境里运行，应该不会轻易碰到 Windows 上的东西。

后来我看见一条路径转换，才意识到自己想错了。项目在 D 盘，进入 WSL 后会出现在 /mnt/d。既然 D 盘能这样访问，C 盘通常也能从 /mnt/c 访问。助手虽然没有直接打开 Windows 命令行，仍可能读写当前用户有权限访问的其他文件。

我想保护的是“只让这次命令接触当前项目”，而 WSL 本身没有替我做到这件事。

## 给每次命令划一个更小的房间

我最后在 WSL 里加了 Bubblewrap。可以把它理解成：每运行一条命令，就临时布置一个只有必要物品的房间。当前项目被放在 /workspace，可以读写；系统文件大多只能读；Windows 磁盘入口 /mnt 在这个房间里是空的；网络默认也被隔开。

外面的 WSL 仍照常工作，仍能访问项目所在的 D 盘。受限制的是助手启动的那条命令。这样不用把整个开发环境都改掉，也不必每次都启动一个完整的 Docker 容器。

项目原本就有一个专门负责运行命令的位置。我只改了 WSL 这条执行路径，让上层的助手继续按原来的方式调用它。这也让新限制集中在最该生效的地方。

## 测试全过了，第一次真跑却失败

写完后，针对这部分的测试通过了；可第一次放到真实 WSL 里运行，就遇到报错：程序想创建 /workspace，根目录却已经被设成只读，根本创建不了。

修复只是在准备环境时先建好这个目录。这个小失误提醒我：测试可以检查命令参数是否正确，却不能替代在真实系统里试一遍。之后我实际确认了几件事：命令能在项目里创建文件，看不到 /mnt/c，不能修改系统目录，也不能正常联网。

这层保护有明确边界。它管的是助手通过 Bash 工具启动的 Linux 命令，不会隔离运行在 Windows 上的助手主程序，也没有 Docker 那样的内存和进程数限制。对风险更高的任务，我仍会选 Docker。

这次最重要的收获是纠正了一个想当然的判断：“运行在虚拟环境里”和“看不到我的文件”是两件事。只有真的去检查命令能看见什么、能改动什么，安全边界才算说清楚。
