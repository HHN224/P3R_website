# 按下 Esc 后，下一句话为什么发不出去？

> 日期：2026-09-15
> 项目：agent-lite，一个我用 Python 练习做的编程助手

我给助手加了一个很自然的操作：它做错方向了，按 Esc 就让它停下。第一次试的时候，屏幕显示“已中止”，我以为事情结束了。直到我接着发出下一句话，模型接口直接拒绝了这段对话。

那一刻我才发现，停下眼前的动作，不等于把这次任务收拾好了。

## 对话里留下了两件“说要做，却没交代结果”的事

我打开保存的对话记录。模型刚刚说要调用三个工具：先读取文件，再修改文件，最后运行测试。第一个工具已经有结果；我在第二个工具执行前按了 Esc，程序直接跳出了循环。记录里于是还留着后两个“我要调用工具”，却没有它们的结果。

对人来说，这段记录不难理解：我叫停了，所以后面没做。但模型接口要求每个工具调用都有对应的结果。缺了两条，整段历史就不再是它能接着读的对话。

这解释了为什么“已中止”显示得很正常，下一句话却发不出去。问题不在下一句话，而在上一次任务留下的半截记录。

## 中止时，把没做的事如实记下来

我把取消过程重新按时间梳理了一遍：如果模型还没提出工具调用，直接结束就好；如果已经提出三个、只完成一个，就要给剩下两个补上“用户已取消，这个调用没有执行”。已经做完的工具保留原结果，绝不能因为收尾而再执行一次。

这里不能偷懒写成“执行失败”。工具没有失败，它根本没运行。若告诉模型失败了，它可能去修一个不存在的故障；若说成功了，又会误以为文件已经改好。留下真实记录，后面的对话才能接得上。

还有一个更细的时刻：如果按 Esc 时，模型连工具名称或参数都还没说完整，那段没说完的调用不能进入正式历史。我也把这种半截信息丢掉，只保留完整的内容。

改完后，我用“在两个工具之间取消，再继续聊天”的测试确认：按 Esc 后仍能发出下一句话。现在我会把“取消”看成一次需要认真收尾的正常操作，而不只是一个让程序跳出的快捷键。
